# 2026-10-17 线上会议：截取会议软件的声音（D-033）

## 范围

接[原型记录](2026-10-17-app-audio-tap.md)。负责人裁决 B-007（“1、是 2、三选一 3、这就要看会议的方式了，还有一种情况是我方现场有多个人，对方是会议 app 也会有多个人 4、可以 5、可以 6、可以”）后，把 `mt-audiotap` 接入会议模式。第 3 条按“现场、线上各选人数、各自区分说话人”实现；第 4 条按“建议戴耳机 + 自动去掉回声”实现（“只用会议软件的声音”本身也是一种来源）。

## 改动

- `mt-audiotap`：`--apps`（正在运行的应用及是否在发声）、`--exclude-bundle`、`--probe`（开会前完成授权）；换输出设备时整个重建截取并按真实时间补静音；监听系统音频进程列表变化立即重新匹配（原来每 2 秒一次，会丢掉开头一两秒）。
- 主进程 `meeting/index.ts`：会议按“路”（`Track`）组织，每路各自临时录音、分句、在线归类、人数、失败重试；只有麦克风一路边录边降噪；两路时用 `alignPad` 按真实时间对齐；麦克风一路先 `echoFree` 去掉外放回声；整理、恢复、按人数重新区分、改名记住声纹、改归属、合并都按路进行。`meeting/app-audio.ts` 管理截取进程（意外退出重启、授权框等待提示、一直静音提示）、应用列表、`prepareAppAudio`。
- 存储：`meetings` 增 `source`、`app_audio_path`、`app_name`、`expected_remote`，`meeting_speakers` / `meeting_segments` 增 `track`（增量补列，旧库兼容）；设置增 `meetingSource`、`meetingApp`、`meetingRemoteSpeakers`。
- 主窗口：开始会议卡片增加声音来源、应用、现场 / 线上人数；会议详情的说话人栏分「现场」「线上」两组各有人数；改归属与合并只列同一组。
- `electron-builder.yml`：`NSAudioCaptureUsageDescription`。
- 顺带修复：FireRedASR2 在噪声上输出的 `< sil >` 被存成文字（`stripAsrTokens`）。

## 验证

- `npm run native`、`npm run typecheck`、`npm run test`（80 项，新增回声 4 项、两路对齐 1 项、特殊记号 1 项）、`npm run build`、`npm run docs:check` 通过。
- 回声门槛标定（`scripts/echo-sim.ts`，WenetSpeech 会议作对方、AISHELL-1 作现场，4 种回声音量 × 2 种混响，各 25 组）：只用整体能量包络时“戴耳机两边同时说”误删 10% → 改为时间 × 16 频带包络后为 0；门槛 0.6：只有回声时去掉 89～98%，先现场后回声时现场保留 100%，两边同时说 + 回声时现场保留 83～95%（回声与现场一样响时 72%）。
- 打包版隔离实例真机外放（扬声器 → 麦克风，Chrome 播放 8 句线上 + 系统朗读 3 句现场，其中 2 句与线上同时说）：线上 8 句都在、现场 3 句全部保留，现场错字率 2.4%；离线复算真实回声的整句相关 0.67～0.87、现场 −0.29～−0.06；线上首句开头被丢 → 改为监听进程列表后复测首句基本完整。第三轮测试时房间里有人说话（被正确记为现场），同时段有两小段回声未去掉，符合“同时说话时保留”的设计。

## 发现与教训

- 用户在授权框点「允许」后，macOS 退出并重新打开了所有 MyTypeless 实例（测试实例和正在用的正式版）。会议中途发生会打断会议 → 改为开会前完成授权（`prepareAppAudio`，授权框没回应时不开始会议）。
- 测试时先开了会议再请用户点授权，用户几小时后才回复，测试会议开着麦克风录满 4 小时，把房间里的对话转写进了测试库；测试实例还监听 Fn，干扰了用户正常听写。以后需要用户操作的步骤放在开始录音之前，测试实例用完立即关闭；测试数据交用户决定是否删除。
